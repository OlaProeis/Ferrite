## 5. Functional requirements — Tier A (must ship)

### 5.1 Stats panic on multi-byte first character ([#171](https://github.com/OlaProeis/Ferrite/issues/171))

**Problem.** `DocumentStats` / list detection panics:

```text
thread 'main' panicked at src\editor\stats.rs:316:49:
called `Option::unwrap()` on a `None` value
```

Root cause: `is_list_item` gates on `trimmed.len() >= 2` (**bytes**), then does `chars().nth(1).unwrap()`. A single multi-byte character (e.g. `§`, `ß`, `ö`, CJK) can have `len() >= 2` with only **one** char → `nth(1)` is `None`.

**Required behaviour.**
- Use character-aware checks (`chars().next()`, `chars().nth(1)`, or `chars().take(2)` collected) — never assume byte length ⇒ char count.
- No `unwrap()` on optional char indices in this path (or any sibling helpers with the same pattern, e.g. ordered-list `after` char).
- Typing the reporter’s repro characters as the first non-whitespace character of a line must not panic.

**Key files:** `src/editor/stats.rs` (`is_list_item`, related helpers ~309–337).

**Acceptance criteria.**
1. Unit tests: lines starting with multi-byte chars (`"§ foo"`, `"ß"`, `"中文"`, `"é item"`) do not panic; `is_list_item` returns `false` unless a real list marker pattern matches.
2. ASCII list markers still detected: `- item`, `* item`, `1. item`.
3. `cargo test` passes; manual: type `§` / `ß` at line start on Windows German layout — no crash.

**Docs:** short note in `docs/technical/editor/` (e.g. extend stats/document-stats doc if one exists, or `document-stats-list-detection.md`) + CHANGELOG Fixed.

**Complexity hint:** 2

### 5.2 Preserve line endings (CRLF / LF) ([#174](https://github.com/OlaProeis/Ferrite/issues/174))

**Problem.** Opening a Windows CRLF `.md` and clicking/editing in the preview marks the file dirty; saving converts the whole file to Unix LF. Cause: buffer rewrites use `str::lines()` + `join("\n")`, which strips `\r` and normalizes to LF.

**Required behaviour.**
- Detect dominant (or first) line ending when loading a file into a `Tab` — store as tab metadata (e.g. `LineEnding::Lf | LineEnding::Crlf`).
- All source rewrite helpers that rebuild the document from lines must rejoin with the tab’s line ending: especially `update_source_range`, `update_code_block`, and any other `lines().collect` + `join("\n")` paths that mutate open markdown buffers (`src/markdown/editor.rs`, `src/app/line_ops.rs`, `src/markdown/formatting.rs` as applicable).
- Dirty detection must not flip solely because of EOL normalization on open (opening a CRLF file and viewing without edits → not modified).
- New files / empty buffers: default to platform conventional ending (Windows → CRLF, else LF) or match settings if one already exists — pick one rule and document it.
- Mixed-EOL files: document chosen policy (prefer: preserve majority / first-line ending; do not invent a perfect mixed-EOL rewriter in v0.3.1).

**Key files:**
- `src/state.rs` — `Tab` fields; load/save paths; `apply_external_disk_reload`
- `src/markdown/editor.rs` — `update_source_range` (~7167), `update_code_block` (~7227), related joins
- `src/app/line_ops.rs`, `src/markdown/formatting.rs` — buffer rebuilds
- File open/save in `src/app/file_ops.rs` as needed

**Acceptance criteria.**
1. Open a CRLF fixture → click heading in preview → **not** dirty from EOL alone; if an intentional content edit occurs, save preserves `\r\n`.
2. Open an LF fixture → save still uses `\n`.
3. Unit tests for detect + rejoin helpers; regression test that `update_source_range` on a CRLF buffer keeps `\r\n`.
4. Manual: Windows repro from #174 passes.

**Docs:** `docs/technical/files/line-ending-preservation.md` (new) + `docs/index.md` + CHANGELOG Fixed.

**Complexity hint:** 7

**Hard dependency note:** Land EOL metadata + join helper **before** or as part of the same epic as sweeping rewrite call sites. Do not fix only one helper and leave others normalizing.

### 5.3 HTML entities in Rendered / Split ([#173](https://github.com/OlaProeis/Ferrite/issues/173))

**Problem.** Since v0.3.0, entities like `&amp;`, `&rarr;`, `&reg;` show as raw text or as `«HTML»` instead of characters. `HtmlInline` currently paints a placeholder and ignores the string (`src/markdown/editor.rs` ~4790–4797).

**Required behaviour.**
- Common named entities and numeric entities (`&#…;`, `&#x…;`) used in GitHub-flavored markdown prose render as their Unicode characters in Rendered/Split.
- Minimum bar: `&amp;` `&lt;` `&gt;` `&quot;` `&nbsp;` `&rarr;` `&larr;` `&reg;` `&copy;` `&mdash;` `&ndash;` `&hellip;` plus numeric forms for the same.
- Do **not** execute or render arbitrary HTML tags via this path — entities only (or entity-only HtmlInline). Dangerous tags stay sanitized/passthrough as today.
- Prefer decoding at parse or at a single inline-render choke point so CSV/export paths stay consistent where applicable.

**Key files:** `src/markdown/editor.rs` (`HtmlInline` branch); `src/markdown/parser.rs` (if entities should become `Text` nodes earlier); optional small `html_entities` helper module.

**Acceptance criteria.**
1. Fixture markdown with `&amp; &rarr; &reg;` renders `& → ®` (glyphs) in Rendered and Split.
2. Regression: v0.2.8-era behaviour restored for the reporter’s examples.
3. Unit tests for the decoder; no panic on unknown entities (leave as literal or soft-fail — document choice).
4. Existing GitHub HTML subset tests still pass.

**Docs:** update `docs/technical/markdown/github-html-subset.md` (or new `html-entities.md`) + CHANGELOG Fixed + `test_md/` fixture snippet.

**Complexity hint:** 4

### 5.4 Arrow navigation in rendered view ([#170](https://github.com/OlaProeis/Ferrite/issues/170))

**Problem.** In Rendered view, Up/Down arrows do not move to the next/previous line or editable block, which blocks using Rendered as a light editor.

**Required behaviour.**
- When focus is in the rendered markdown preview (not inside a nested text edit field that already handles arrows), **ArrowDown** moves to the next navigable block/line and **ArrowUp** to the previous.
- If a block is in click-to-edit / session edit mode, arrows should move the caret within the block when appropriate; at block boundaries, move to adjacent block (match common WYSIWYG expectations; document the chosen model).
- Do not break Raw editor arrow behaviour or Split raw pane.
- Respect preview lock: navigation still works when locked; edits remain gated.

**Key files:** `src/markdown/editor.rs` (keyboard handling around structural keys); `src/app/central_panel.rs` (focus routing); related rendered-edit session code.

**Acceptance criteria.**
1. Open a multi-paragraph doc in Rendered → Down/Up moves through content without sticking on one line.
2. Split view: raw pane arrows unchanged; preview pane arrows navigate preview.
3. Manual row added to `docs/technical/platform/v0.3.1-test-checklist.md` (e.g. `UX-arrow-nav`).

**Docs:** short section in rendered-edit docs (e.g. `rendered-edit-session-paragraphs-lists.md` or new `rendered-arrow-navigation.md`) + CHANGELOG Fixed.

**Complexity hint:** 6

### 5.5 Find: scroll to match in Rendered + query select-all ([#175](https://github.com/OlaProeis/Ferrite/issues/175))

**Problem.** Ctrl+F in Rendered View shows match counts / highlights but the viewport does not advance to successive matches (Enter / F3). Raw mode works. Also, focusing the find box appends to the previous query instead of selecting it for replacement.

**Required behaviour.**
- When `scroll_to_match` / find-next/prev fires in Rendered or Split preview, convert the current match’s byte (or line) range into a scroll target and scroll the preview so the match is visible (reuse or extend `scroll_to_line` plumbing in `MarkdownEditor`).
- Highlights already painted via `search_highlights` must stay in sync with the current match index.
- Opening Find (Ctrl+F) focuses the query field and **selects all** existing query text so typing replaces it (standard editor behaviour).

**Key files:**
- `src/markdown/editor.rs` — `search_highlights`, `scroll_to_line` (~1088), paint helpers
- `src/app/central_panel.rs` — passes `scroll_to_match` / highlights
- `src/app/find_replace.rs`, `src/editor/find_replace.rs` — focus / select-all
- `src/state.rs` / UI flags for `scroll_to_match`

**Acceptance criteria.**
1. Rendered: Ctrl+F → type query → Enter/F3 cycles matches and **viewport moves** to each.
2. Split: same for the preview side (raw side already OK).
3. Ctrl+F with an existing query selects the query text (next keystroke replaces).
4. Checklist row + CHANGELOG Fixed.

**Docs:** update find/replace technical doc if present, or `docs/technical/editor/find-in-rendered.md`.

**Key files:** `src/platform/macos.rs`, `src/platform/mod.rs`, `src/main.rs` / app init, file-open routing in `src/app/file_ops.rs` / `mod.rs`.

**Acceptance criteria.**
1. On a macOS dev machine: Open With → file appears in a tab **or** documented escape hatch accepted with CHANGELOG + install doc update.
2. CLI open path remains unbroken.

### 6.3 Emoji font fallback ([#168](https://github.com/OlaProeis/Ferrite/issues/168))

**Problem.** Emoji often fail to render (tofu / missing glyphs) because Inter / JetBrains Mono stacks lack emoji; no emoji fallback is registered in `src/fonts.rs`.

**Required behaviour.**
- Register a system (or bundled) emoji-capable font as a **fallback** on Proportional and Monospace families used by the editor and markdown preview.
- Prefer OS fonts when present (e.g. Segoe UI Emoji on Windows, Apple Color Emoji on macOS, Noto Color Emoji on Linux) with graceful skip if missing.
- UI Phosphor icons remain the icon system — this task is **Unicode emoji in document text**, not replacing Phosphor.
- No network download of fonts at runtime.

**Key files:** `src/fonts.rs`; theme/font init in app startup; spot-check `src/ui/file_tree.rs` comments on emoji failure.

**Acceptance criteria.**
1. Document containing `😀 ✅ ⚠️` shows color or at least monochrome emoji glyphs in Raw and Rendered on Windows (primary) and does not regress CJK fallback.
2. Missing emoji font on a locked-down system does not panic (skip fallback).
3. CHANGELOG Added; short `docs/technical/ui/emoji-font-fallback.md` (or fonts doc update).

### 6.4 Tab / Shift+Tab indent selection ([#177](https://github.com/OlaProeis/Ferrite/issues/177))

**Problem.** In the raw Ferrite editor, Tab always inserts `"\t"` at cursors (`src/editor/ferrite/editor.rs` ~2618–2622) and does not indent/outdent a multi-line selection. (Rendered list Tab indent is a different feature and already exists — do not confuse them.)

**Required behaviour.**
- When the selection spans one or more lines (or a non-empty selection), **Tab** indents each selected line; **Shift+Tab** outdents.
- Respect editor settings: `use_spaces` / `tab_size` (indent with N spaces or a tab character).
- Outdent removes one indent step when present; no-op at column 0.
- When selection is empty (caret only), keep inserting a single indent (tab or spaces per settings) — fix the TODO about `use_spaces` / `tab_size` if still present.
- Multi-cursor: apply consistently to all cursors/selections.
- Record undo as one logical edit when indenting a block selection.

**Key files:** `src/editor/ferrite/editor.rs` (Tab key branch); possibly `src/editor/ferrite/input/`; settings for `use_spaces` / `tab_size`.

**Acceptance criteria.**
1. Select three lines → Tab indents all three; Shift+Tab restores.
2. Soft-tabs setting uses spaces; hard-tabs use `\t`.
3. Empty selection still inserts indent; focus does not jump to other UI widgets.
4. Unit tests for indent/outdent helpers; CHANGELOG Added.

**Docs:** `docs/technical/editor/indent-selection.md` (new) or ferrite-editor input doc + `docs/index.md`.

**Complexity hint:** 4
